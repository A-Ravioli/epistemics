# Research: technical stack for web + Tauri 2 desktop with a shared codebase

Versions checked against npm and crates.io on 2026-09-16 unless noted. Several vendor documentation sites (Tauri, AI SDK, Drizzle, PowerSync) were unreachable during research; those facts come from GitHub, the registries, and secondary sources, and are flagged where they could not be verified first-hand.

> **Design decision recorded in DESIGN.md:** this report recommends Vercel's AI SDK as the LLM client layer. The design instead uses the official `@anthropic-ai/sdk` directly behind a small `LlmProvider` interface (see DESIGN.md §8). Reason: the tutor relies on structured outputs (`messages.parse`), citations, prompt caching with explicit breakpoints, and `output_config.effort`, which the official SDK exposes first; a local Ollama provider is a small second implementation of the same interface. Everything else in this report stands.

## 1. Tauri 2 state

- **Versions**: `tauri` 2.11.5 (crates.io updated 2026-09-15), `tauri-cli` 2.11.4, `@tauri-apps/api` 2.11.1. The `next` npm tag now points at `3.0.0-alpha.0` for the core packages and every official plugin (published ~2026-09-12). 3.0 is early alpha (first change noted: `default_runtime` macro removed, generics default to `tauri::DynRuntime`); stay on 2.11 for a production app but keep plugin surface thin so the v3 move is cheap. Sources: [Tauri all versions](https://v2.tauri.app/release/tauri/all-versions/), [3.0 milestone](https://github.com/tauri-apps/tauri/milestone/5), [tauri-v3.0.0-alpha.0](https://newreleases.io/project/github/tauri-apps/tauri/release/tauri-v3.0.0-alpha.0).
- **Mobile**: iOS/Android are stable in 2.x, but not every plugin/feature is ported ([Tauri 2.0 release post](https://v2.tauri.app/blog/tauri-20/)). Not needed for the web+desktop target, but the same codebase could go there later.
- **Official plugins (npm / crate, all 2.x, all ESM)**: `plugin-sql` 2.4.1 (sqlx 0.9 under the hood; `Database.load("sqlite:app.db")`, `execute`, `select`, Rust-side migrations via `Builder::add_migrations`; **no SQLite extension loading**, see [plugins-workspace#2622](https://github.com/tauri-apps/plugins-workspace/issues/2622)), `plugin-store` 2.4.5 (JSON prefs, not secrets), `plugin-fs` 2.5.2 (scoped by capabilities), `plugin-http` 2.6.1 (Rust reqwest-backed `fetch`; bypasses CORS; needs `http:default` capability with a URL allowlist), `plugin-dialog` 2.7.3, `plugin-updater` 2.11.0 (signed updates; pair with `plugin-process` for relaunch), `plugin-opener` 2.5.5, `plugin-notification` 2.4.0, `plugin-stronghold` 2.3.2 (**"no longer recommended, will be removed in v3"** per the [Stronghold plugin page](https://v2.tauri.app/plugin/stronghold/)).
- **Secrets**: use the OS keychain. Simplest: a ~30-line Tauri command wrapping the `keyring` crate 4.2.0 (enable `apple-native`, `windows-native`, `sync-secret-service`/`linux-native` features). Packaged options: [`tauri-plugin-keyring-store`](https://docs.rs/tauri-plugin-keyring-store/latest/tauri_plugin_keyring_store/) 0.2.0 (Stronghold-shaped API over the keychain) or [HuakunShen/tauri-plugin-keyring](https://github.com/HuakunShen/tauri-plugin-keyring) 0.1.0 (old).
- **One frontend build for browser and Tauri**: build `apps/web` once with Vite; Tauri's `build.frontendDist` points at that `dist/` and `build.devUrl` at the Vite dev server. Detect at runtime with `isTauri()` from `@tauri-apps/api/core` (since 2.5.0 it reads `globalThis.isTauri`, so it is unit-test friendly; `window.__TAURI_INTERNALS__` is the lower-level signal). Sources: [core namespace](https://v2.tauri.app/reference/javascript/api/namespacecore/), [tauri-docs#1870](https://github.com/tauri-apps/tauri-docs/issues/1870). Put every platform-specific thing behind one `Platform` interface (`db`, `secrets`, `files`, `llmFetch`, `updater`) and lazy-`import()` the Tauri implementation only when `isTauri()` is true so the browser bundle does not carry plugin code.
- **IPC patterns**: `invoke()` for request/response; `ipc::Response` for raw `Vec<u8>` (no JSON/base64 overhead); `Channel<T>` (JS `new Channel()` with `onmessage`, Rust `tauri::ipc::Channel<T>`) for push streaming of LLM tokens or progress. Small payloads are eval'd into the webview, large ones are fetched via an internal channel queue, so `Channel` is the right tool for token streams. Sources: [channel.rs](https://docs.rs/tauri/latest/src/tauri/ipc/channel.rs.html), [DeepWiki IPC overview](https://deepwiki.com/tauri-apps/tauri/4.1-ipc-protocol-and-invoke()-system). Sidecars: `bundle.externalBin` + `plugin-shell` `Command.sidecar()` with target-triple-suffixed binaries; use only for things you cannot do in-process (e.g. bundling `llama-server`).
- **Limitations to design around**: (1) The webview origin is `tauri://localhost` on macOS/Linux but `http://tauri.localhost` on Windows, which affects CORS allowlists (e.g. `OLLAMA_ORIGINS`), cookies and `postMessage` checks ([tauri#8339](https://github.com/tauri-apps/tauri/issues/8339), [tauri#6869](https://github.com/tauri-apps/tauri/issues/6869)). (2) No Node in the frontend; anything native goes through Rust commands or a sidecar. (3) Engine drift: WKWebView (macOS) follows the OS Safari; WebView2 (Windows) is evergreen Chromium; WebKitGTK (Linux) is the weakest (no WebGPU, weaker perf). Test on all three. (4) CSP is set in `tauri.conf.json` (`app.security.csp`); `connect-src` must include any host the webview fetches directly. (5) For SPA routing, use hash or memory history in Tauri, or verify that the custom-protocol handler falls back to `index.html` for deep links after reload.

## 2. Storage strategy for "same code in web and desktop"

**Recommendation: Drizzle ORM over one `DbExecutor` interface, with two executors.**

```ts
interface DbExecutor { run(sql: string, params: unknown[], method: 'run'|'all'|'get'|'values'): Promise<{rows: unknown[]}> }
// desktop: tauri-plugin-sql (later: custom rusqlite command)
// web: @sqlite.org/sqlite-wasm in a Worker (or SQLocal)
const db = drizzle(async (sql, params, method) => executor.run(sql, params, method), { schema });
```

Rationale:
- Drizzle's `sqlite-proxy` driver is official and is exactly a callback ([drizzle-orm/src listing](https://github.com/drizzle-team/drizzle-orm/tree/main/drizzle-orm/src) has `better-sqlite3`, `bun-sqlite`, `libsql`, `sql-js`, `sqlite-proxy`, `expo-sqlite`, `op-sqlite`, `durable-sqlite`, `d1`; **there is no official Tauri or sqlite-wasm driver**). The Tauri community pattern is `sqlite-proxy` -> `invoke` ([tdwesten demo](https://github.com/tdwesten/tauri-drizzle-sqlite-proxy-demo), [Kunkun write-up](https://docs.kunkun.sh/blog/tauri--drizzle-proxy/)). On the web, SQLocal ships `SQLocalDrizzle` (a `driver` for the same proxy mechanism) and `SQLocalKysely` ([sqlocal](https://github.com/DallasHoff/sqlocal), 0.18.0). Using one driver on both platforms means identical query semantics; only the executor differs.
- Schema lives in `packages/db` as Drizzle tables; `drizzle-kit generate` emits SQL migration files that both executors apply (Rust `add_migrations` on desktop, a small JS runner in the browser). Caveat: the proxy driver has no `db.transaction()`; expose `begin/commit` or a `batch` on the executor.
- Drizzle 1.0 is at `1.0.0-rc.5` (RQB v2 with `defineRelations()`, RQB v1 removed). Pin 0.45.2 now or adopt the RC deliberately; do not float.
- Kysely (0.29.6) is a good alternative if you prefer a query builder to an ORM; [kysely-sqlite-tools](https://github.com/subframe7536/kysely-sqlite-tools) already has a Tauri SQL plugin dialect and wasm/wa-sqlite dialects, and SQLocal has a Kysely dialect.

**Browser persistence facts (verified)**:
- `@sqlite.org/sqlite-wasm` 3.53.4-build1 (2026-09-08). The `opfs` VFS needs `SharedArrayBuffer`, i.e. COOP/COEP headers, and **Safari cannot use it** (WebKit never shipped `credentialless`, and its file locking is too coarse for multi-tab). The `opfs-sahpool` VFS needs no COOP/COEP and works in Safari 17+/WKWebView, but is single-connection (no multi-tab). SQLite 3.53 added an `opfs-wl` VFS. Sources: [sqlite persistence doc](https://sqlite.org/wasm/doc/trunk/persistence.md), [sqlite-wasm news](https://sqlite.org/wasm/doc/trunk/news.md), [SQLite forum thread on Safari/Firefox](https://sqlite.org/forum/forumpost/046467088aeda708). Practical rule: default to `opfs-sahpool` in a dedicated Worker, use Web Locks to make one tab the DB owner, and fall back to wa-sqlite's IDBBatchAtomicVFS (wa-sqlite 1.0.0) or in-memory for private mode.
- `sqlocal` 0.18.0 wraps the official wasm build in a worker with OPFS; its docs say cross-origin isolation is required for its default VFS, so if you need Safari without COOP/COEP go directly to `@sqlite.org/sqlite-wasm` with `opfs-sahpool`.
- `@libsql/client-wasm` 0.18.0 exists but only the worker variant does OPFS and it does not sync from the browser, so libSQL is not a "same code" path.
- PGlite 0.5.8 (v0.4 added PostGIS and multiplexing; 10M weekly downloads) is excellent but is Postgres-in-wasm, so it does not share a file format with a desktop SQLite; skip unless you want Postgres everywhere (then you would run PGlite in Tauri too via a sidecar, which is heavier). Sources: [PGlite v0.4](https://electric.ax/blog/2026/03/25/announcing-pglite-v04).

**Sync options (only if/when needed)**:
- **PowerSync** (`@powersync/web` 2.3.1): Postgres/MongoDB -> on-device SQLite, has explicit Safari guidance (`OPFSCoopSyncVFS` for multi-tab) but requires its own SQLite build with the PowerSync extension on every platform, so it replaces your executor rather than plugging into it. Best if you have a Postgres backend and want managed sync. [PowerSync web SDK](https://docs.powersync.com/client-sdks/reference/javascript-web).
- **Turso embedded replicas / offline writes** via [`tauri-plugin-libsql`](https://github.com/HuakunShen/tauri-plugin-libsql) 0.1.0 (encryption + Drizzle + migration runner): desktop-only, and the README warns embedded-replica encryption is silently disabled by an upstream libsql bug (fix only on a git branch). Not a web path.
- **Evolu** 11.0.3: SQLite + CRDT + E2E-encrypted relay, runs on sqlite-wasm in browser and can run in a webview; you must adopt its schema/DB layer wholesale. Good fit for single-user multi-device with zero backend logic.
- **Zero** 1.9.0 (1.0 GA June 2026) and **Electric** are Postgres-first query-sync engines (Zero persists in IndexedDB, not SQLite) and need a server component; **TinyBase** 9.7.1 is a reactive KV store with sqlite persisters, fine for small app state, not a document corpus; **cr-sqlite** last commit June 2026 but its tooling (vlcn-orm) is stale since 2024, and it needs a loadable extension (not possible in tauri-plugin-sql or stock wasm). Sources: [Zero 1.0](https://www.infoq.com/news/2026/06/zero-version-1/), [Electric alternatives page](https://electric-sql.com/docs/reference/alternatives), [cr-sqlite](https://github.com/vlcn-io/cr-sqlite).
- **Recommendation**: keep sync out of v1 but make the schema sync-ready (UUIDv7 primary keys, `updated_at`/HLC column, soft-delete tombstones, content-addressed blobs for documents, an `outbox` change-log table). When you add sync, a per-row LWW protocol against a small Hono/Postgres (or Turso) server is a few hundred lines and works identically from both executors; Evolu is the off-the-shelf choice if you want E2E encryption without writing a server.

## 4. LLM architecture for local-first

**Principle: one shared TypeScript LLM layer (`packages/llm`), with the API key and network hop injected per platform via the client's `fetch` option.**

- **Web**: the key lives only on a thin server (Hono on Node 22/Cloudflare Worker/Bun). Two shapes: (a) a `/api/chat` endpoint where the server runs the model call and returns a stream; or (b) a pure passthrough proxy `/api/anthropic/*` that injects `x-api-key`, enforces per-user auth and budgets, and streams SSE back, with the client configured with `baseURL: '/api/anthropic'` so the client code is identical to desktop. (b) keeps prompt assembly client-side and shared; choose it.
- **Desktop**: key in the OS keychain (section 1). Do not hand the key to webview JS. Instead implement `llm_fetch` as a Tauri command: JS passes `{url, method, headers, body}`, Rust checks the host against an allowlist (`api.anthropic.com`, `localhost:11434`), adds `x-api-key` from `keyring`, performs the request with `reqwest` 0.13, and streams response bytes back over a `tauri::ipc::Channel<Vec<u8>>`; JS wraps the channel in a `ReadableStream` and returns a `Response`, so a client constructed with `fetch: tauriLlmFetch` works unchanged. This avoids CORS entirely, keeps the key out of the webview, and needs no `dangerous-direct-browser-access` header. `@tauri-apps/plugin-http`'s `fetch` is the lower-effort variant (it reads bodies through IPC so SSE streaming works), but the key would then be in JS; use it only for a BYOK power-user mode.
- **Models and features** (from the Anthropic reference, cached 2026-06): default to `claude-opus-5` ($5/$25 per MTok, 1M context, adaptive thinking on by default, `output_config.effort` low..max); `claude-sonnet-5` ($2/$10) for bulk/summarization; `claude-haiku-4-5` ($1/$5) for classification/routing. Structured outputs: `output_config: { format: {...JSON schema} }` (the old `output_format` is deprecated) and `strict: true` on tool definitions. Prefill is rejected on 4.6+ models, so use structured outputs, not prefill, for JSON. Citations: `citations: { enabled: true }` on `document` blocks gives `page_location`/`char_location` back, ideal for "answer from the textbook with page refs".
- **Prompt caching for long textbook context**: cache is a byte-exact prefix match over `tools -> system -> messages`; up to 4 `cache_control` breakpoints; `{"type":"ephemeral","ttl":"1h"}` for a study session; minimum cacheable prefix is model-dependent (512 to 4096 tokens). Put the chapter/document block first with a 1h breakpoint, the frozen system prompt before it, and the per-turn question last; never interpolate timestamps/IDs into the prefix; keep the tool list deterministic; use mid-conversation `role: "system"` messages (Opus 5/Fable) instead of editing the top-level system prompt. Verify with `usage.cache_read_input_tokens`.
- **Cost control**: log `usage` per call into a `llm_calls` table (model, input/cache-read/cache-write/output tokens, computed cost) and enforce per-day budgets in-app; use the Batches API (50% off, async) for ingestion-time work (chapter summaries, question generation, tagging); use `effort: "low"|"medium"` for routine turns; count tokens with `/v1/messages/count_tokens` before sending huge contexts; prefer caching one big context over RAG-ing tiny chunks when a whole chapter fits.
- **Pluggable local provider**: Ollama exposes `/api/chat` with a JSON-schema `format` (grammar-constrained decoding) and an OpenAI-compatible `/v1` ([Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs)); llama.cpp's `llama-server` speaks OpenAI-compatible with `response_format: json_schema`. Route local calls through the same `llm_fetch` command on desktop (Ollama's CORS allowlist would otherwise need `tauri://localhost` and `http://tauri.localhost`). Bundling `llama-server` as a Tauri sidecar is possible but desktop-only. Model the provider as `LlmProvider { chat(), structured(), embed?() }` in `packages/llm` and select by settings.

## 5. Document ingestion

- **PDF**: `pdfjs-dist` 6.3.289 (ESM, run in a Worker; `getDocument` -> `page.getTextContent()`; also `getOutline()` for headings). Works in both webviews. Desktop optimization later: Rust `pdfium-render` or `pdf-extract` behind a command for large books.
- **EPUB**: `epubjs` 0.3.93 is unmaintained (2022). Use `foliate-js` 1.0.1 (modular ESM parsers for EPUB/MOBI/FB2/CBZ, "API may change") for parsing + TOC, or do it directly: EPUB is a zip (`fflate`/`@zip.js/zip.js`) + OPF/NCX/XHTML parsed with `DOMParser`; extract per-spine-item text with heading structure. Same code both platforms.
- **DOCX**: `mammoth` 1.12.3 has a browser build (`convertToHtml`/`extractRawText`).
- **Markdown**: parse with `remark` (unified) to get a heading tree for chunk boundaries.
- **OCR fallback**: if a page's extracted text is below a threshold, render the page to a canvas with pdf.js and run `tesseract.js` 7.0.0 (WASM, large; lazy-load, cache language data). On desktop you could optionally sidecar native Tesseract for speed.
- **Chunking**: structure-aware first (heading path from EPUB TOC / PDF outline / markdown headings), then size-bound ~400-800 tokens with ~10-15% overlap; store `chunks(doc_id, ordinal, heading_path, page_start, page_end, text, token_count, hash)`; keep the original per-page text for citation display. Use a JS tokenizer estimate for chunking and Anthropic `count_tokens` for budget decisions.
- **Embeddings**: `@huggingface/transformers` 4.3.0 (v4 released 2026-02-09; WebGPU default where available, BERT-class embedders up to 4x faster; models: `nomic-ai/nomic-embed-text-v1.5` 768d, `Xenova/bge-small-en-v1.5` 384d, `Xenova/all-MiniLM-L6-v2` 384d) in a Worker; works identically in browser and webview (WebGPU on WKWebView/WebView2; WebKitGTK falls back to WASM). Source: [Transformers.js v4](https://roboaidigest.com/posts/2026-02-11-transformers-js-v4-webgpu/). Anthropic has no embeddings API; Voyage AI is the hosted option if you want server-side embeddings.
- **Vector search**: `sqlite-vec` is 0.1.9 (2026-03-31, pre-1.0). Desktop: `tauri-plugin-sql` cannot load extensions; you need a custom `rusqlite` command with the `sqlite-vec` crate registered via `sqlite3_auto_extension` (this is the main reason to eventually replace plugin-sql with your own executor; the `DbExecutor` boundary makes that a contained change). Web: wasm SQLite cannot dynamically load extensions, so sqlite-vec must be compiled into a custom sqlite-wasm build; `sqlite-vec-wasm-demo` 0.1.9 exists but is explicitly a demo ([sqlite-vec wasm page](https://alexgarcia.xyz/sqlite-vec/wasm.html)). **Recommendation**: store embeddings as `BLOB` (Float32Array) in a normal table and do brute-force cosine in a Worker on both platforms first (tens of thousands of 384/768-d vectors search in tens of ms); add sqlite-vec on desktop only when corpora outgrow that. Use SQLite FTS5 (available in both sqlx-bundled and wasm builds) for hybrid lexical search.

Tauri desktop e2e via WebDriver is weak on macOS (no official WKWebView driver; a community one appeared Feb 2026), so keep desktop-specific logic thin and covered by Rust unit tests plus manual smoke on the three engines.

## Key tradeoffs and open verifications

1. `tauri-plugin-sql` vs custom `rusqlite` executor: plugin-sql is zero Rust but blocks sqlite-vec/custom functions; the executor boundary lets you switch later without touching queries.
2. Safari/WKWebView OPFS: only matters for the browser build (desktop uses native SQLite). Use `opfs-sahpool` + a single owner tab via Web Locks; this is the one place browser and desktop behave differently and it is hidden inside the web executor.
3. AI SDK 7 vs raw `@anthropic-ai/sdk`: AI SDK gives provider swapping and `useChat`; raw SDK gives day-one access to every Anthropic feature (structured outputs via `messages.parse`, citations, caching breakpoints, effort). The design picks the raw SDK behind a provider interface.
4. Drizzle 1.0 RC timing: pin `0.45.2` now, or start on `1.0.0-rc.5` if you want RQB v2 and are willing to track RCs.
5. Could not fetch first-hand (blocked): Tauri docs site, AI SDK docs site, Drizzle docs site, PowerSync blog.
